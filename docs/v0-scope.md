# Vulcan v0 — Small Harness, Real Research

Status: **Active scope** (supersedes the v0 phasing in `architecture.md`; that
document remains as the long-term vision archive)
Date: 2026-10-03

## 1. What v0 actually is

A **small harness on top of Pi** that does exactly three things:

1. **Waste less tokens** — learn which tool/MCP calls were bad choices, and
   shape them out.
2. **Route 3 models well** — 2 local, 1 cloud, learned from your own traces.
3. **Give you a research substrate** — your own trace data, a measurable
   target, and a loop you can run experiments on with local models.

Research-first, product-second, local-first. Nothing else in v0.

```
Pi (vulcan-pi extension)
   │  tool calls, tokens, model, outcomes
   ▼
Vigil  (already built — recorder)
   │
   ▼
vulcan-learn  (the research core)
   ├─ waste analyzer   → labels every tool call from the trace
   ├─ router bandit    → learns model choice per task
   └─ policy export    → rules file the extension reads next session
```

The loop: **run → record → label → learn → enforce → run better.**
No experiment engine, no governor, no memory store, no self-modification.

## 2. The three components

### 2.1 `vulcan-pi` — the extension (observer + enforcer)

TypeScript Pi extension. Wraps every tool/MCP call and records:

```json
{
  "run_id": "...",
  "turn": 12,
  "tool": "mcp.filesystem.read",
  "args_hash": "h3f2...",
  "args_summary": {"path": "src/app.ts"},
  "result_bytes": 48211,
  "duration_ms": 340,
  "model": "qwen3-8b",
  "tokens_in": 3200,
  "tokens_out": 410,
  "status": "ok",
  "result_hash": "a91c..."
}
```

Plus run lifecycle events (started / completed / failed) and the model chosen
per turn. Emits to Vigil via the existing ingest API.

It also **enforces**: the router's model choice, repeat-call blocks, result-size
caps, and nudges — all read from a small policy file the learner regenerates.

### 2.2 Router — 3 models, cold start → bandit

| Tier | Model | Use |
|---|---|---|
| L1 | local small (e.g. Qwen3-8B) | trivial, single-file, quick edits |
| L2 | local mid (e.g. Qwen3-14B) | multi-file, tests, moderate reasoning |
| L3 | cloud | architecture, long-horizon, repeated local failures |

**Cold start = rules** (task class from prompt heuristics, files touched,
failure count). Then a **contextual bandit** takes over:

```
state   = {task_class, files_touched, failure_count, tokens_so_far}
action  = {L1, L2, L3}
reward  = success − λ · tokens          (Thompson sampling)
```

Escalation is built in: local fails twice → L2 fails twice → cloud. Every
routing decision is logged as evidence, so you can answer "did the bandit beat
the hand rules?" — that's your first research result.

### 2.3 `vulcan-learn` — waste analyzer + policy learner

The key design choice: **waste labels come from the trace, deterministically.
No LLM needed for labeling in v0.**

| Waste class | How it's detected from the trace |
|---|---|
| **Failed call** | `status != ok` (needed a retry) |
| **Repeat call** | same `tool` + `args_hash` within N turns |
| **Oversized result** | top-k% by `result_bytes`, never truncated/paged |
| **Unused result** | `result_hash` never referenced by any later edit/tool/test event (heuristic — log confidence) |
| **Wrong model** | cloud used for a trivial task; or local failed then cloud redid the same work (double spend) |

Output:

```
vulcan waste <run_id>        # per-run breakdown: where the tokens went
vulcan waste --last 50       # aggregate across runs
```

```
run 3f8a — 214k tokens
  repeat calls        38k  (6 calls, avg 6.3k)
  unused results      51k  (14 results)
  oversized results   44k  (3 results)
  cloud redid local    39k
  failed calls         12k
  ─────────────────────────
  addressable         184k  (86%)
```

Then it exports the policy the extension enforces:

```yaml
# policy.yaml — regenerated by vulcan-learn, read by vulcan-pi
routing:
  L1: {task_class: [trivial, docs], max_files: 1}
  L2: {task_class: [bugfix, feature, test]}
  L3: {task_class: [architecture, research], min_tokens_estimate: 40000}
escalation:
  local_failures: 2
  L2_failures: 2
tool_shaping:
  block_repeats_within_turns: 3
  max_result_bytes: 20000        # larger → paginate/truncate
  nudge_unused: true             # warn before re-reading a big unused file
```

This is not the "YAML fantasy" — it's a **learned routing table + shaping
rules over a policy space you can measure**, regenerated from evidence.

## 3. What this gives you as research

Three questions you can actually answer with local models:

- **RQ1:** Can a bandit router beat hand rules on *cost per successful task*
  on your own workload?
- **RQ2:** How prevalent is each waste class in real runs, and how much can
  deterministic shaping (repeat-block, size caps, pagination nudges) cut
  tokens *without hurting task success*? — a replication of SoL-Pi's findings
  on your own data.
- **RQ3 (later):** Does retrieving lessons from past runs reduce repeat
  mistakes? (first step toward the memory layer, only if RQ2 lands)

Every question has a metric, a baseline, and a cheap local-model experiment
path. That's real research, publishable-in-a-blog-post scale, running on your
Mac.

## 4. Explicitly cut from v0

| Cut | Why |
|---|---|
| Memory / experiences store | RQ3 decides if it's worth it |
| Experiment engine + governor + replay | Only if RQ1/RQ2 show a policy space worth searching |
| Behavioral eval suite | Replaced by "cost per successful task" + task success on real runs |
| Laya | Extra moving parts; deterministic trace labels are better first. Revisit if classification needs get harder |
| Self-modification (L1–L3) | Not the thesis anymore |
| UI | Vigil's UI already shows the events |

`architecture.md`, `memory.md`, `self-improvement.md`, `laya-integration.md`,
`decision-routing.md` stay as the **vision archive** — build those parts only
when the evidence asks for them.

## 5. Milestones

| M | Ship | Proves |
|---|---|---|
| **M1** | `vulcan-pi` emits tool-call events to Vigil; `vulcan waste` CLI | You can see where tokens actually go |
| **M2** | Router v0 (rules + escalation); per-model cost in Vigil | Model spend is visible and steerable |
| **M3** | Bandit router trained on your logs; A/B vs rules | RQ1 answered |
| **M4** | Policy v1: repeat-block, size caps, nudges; measure Δtokens | RQ2 answered |
| **M5** | Decide next: memory (RQ3) vs deeper research vs product | Evidence-gated fork |

M1+M2 is roughly a week of focused work. M3–M4 is where the research lives.
